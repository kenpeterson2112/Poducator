# Background/lock-screen playback — considered, deferred

**Status:** Not built. Deliberately. This is a decision record, not a bug report — the
next person to ask "why doesn't this keep playing when I lock my phone" should land
here, not re-derive the answer from scratch.

## The problem

A podcast that stops the moment you lock your phone or switch apps isn't really a
podcast. Poducator's audio is generated by the browser's own `speechSynthesis` API,
run entirely client-side — and that's the reason it can't do this. A real `<audio>`
element gets a special exemption from mobile OSes: through the Media Session API, the
browser tells iOS/Android "there's an active media session," which is what keeps a
real podcast app or Spotify's web player going through a lock screen.
`speechSynthesis` isn't wired into that system in most browser implementations. The OS
just sees an inactive background tab and suspends it — audio included.

By platform:

- **iOS Safari** (and everything on iOS, since it's all WebKit) — the strictest case.
  Locking the screen suspends the tab's JS almost immediately, `speechSynthesis`
  included. True even for a homescreen-installed PWA in most configurations.
- **Android Chrome** — looser, but not reliable. Background-tab throttling delays the
  JS callbacks the line-by-line playback loop depends on (`onend` between lines), so
  even when audio doesn't outright stop, it can stutter or desync.
- **Desktop** — generally fine. Desktop OSes don't suspend background tabs' audio, and
  locking a computer doesn't stop audio playback at the OS level.

So this is specifically a mobile, screen-locked/backgrounded limitation. Foreground use
in the browser is unaffected either way.

## What it would actually take

The good news, worked out before deciding not to do it: **this does not require
rearchitecting the chapter/checkpoint structure.** `js/tts.js` has a narrow public
surface — `speakChapter(lines, onLineStart)`, `speakOne(line)`, `stop()` — and every
consumer of it (`teach()`'s adaptive loop, checkpoints, and all of the player-controls
work: rewind, restart, review, speed, the ready-gate, the wrap-up bar) is built on top
of that surface, not on `speechSynthesis` directly. They react to a chapter finishing
or being stopped; they don't know or care how a line's audio gets produced.

That makes this a **`tts.js` internals swap**, not an app-wide rewrite:

1. **Server:** one new action on the existing Supabase Edge Function (which already
   proxies Claude calls the same way) — `action: 'speak'`, taking `{ text, voice }`,
   returning real audio bytes from a TTS provider. One new secret (`TTS_API_KEY`),
   same passphrase gate already in front of `generate`.
2. **Client:** `speakLine()` becomes fetch-audio → `new Audio(blobUrl)` → `.play()` →
   wait for the `ended` event, replacing `speechSynthesis.speak()` → `onend`. Same
   cancellation-session handshake `stop()` already uses (`audioEl.pause()` instead of
   `speechSynthesis.cancel()`). `speakChapter`'s loop, `speakOne`, `stop` — signatures
   unchanged. The existing player-controls test suite should keep passing against the
   new internals without modification, which is a strong regression signal for free.
3. **Media Session API:** `navigator.mediaSession.metadata` + action handlers for
   play/pause/previoustrack/nexttrack/seekbackward/seekforward, wired straight to the
   already-existing `onPrevious`/`onSkip`/`onRewindLines`/`onForwardLines` handlers.
   This is the piece that actually produces lock-screen controls and keeps the OS from
   suspending the tab — not a side effect, the mechanism.

Real open decisions that would need answers before building, not blockers:

- **Provider.** OpenAI `tts-1`, Google Neural2, and Amazon Polly Neural all land in the
  same ballpark on price and quality for two-voice dialogue; ElevenLabs sounds
  noticeably more "acted" but costs 5–10x more per character and adds a subscription
  floor on top of usage — not clearly worth it for explanatory dialogue rather than
  narrative performance.
- **Caching.** Rewind/restart/review (all shipped features) would naively re-hit the
  TTS API for lines already spoken. Cache each line's audio blob in memory for the
  run's lifetime — cheap to add, avoids real waste.
- **Saved sessions.** Embedding audio in a `.poducator` file would balloon it from
  tiny JSON to megabytes and breaks the demo-mode "zero external requests" guarantee.
  Recommendation if this is ever built: live lessons get real audio; saved-file replay
  keeps using `speechSynthesis`, same as today.
- **Fallback.** If real-audio synthesis fails for a line, degrade to `speechSynthesis`
  for just that line — matches the app's existing "a stalled lesson is the one failure
  a learner cannot work around" philosophy.

## Cost (researched, not guessed — September 2026 pricing)

This is genuinely cheap at the scale this project runs at:

| Provider / tier | $ / 1,000 chars | ~$ / standard lesson (~11,000 chars) | ~$ / month, 30 students × 2 lessons |
|---|---|---|---|
| OpenAI `tts-1` | $0.015 | $0.17 | ~$10 |
| Google Neural2 | $0.016 | $0.18 | ~$11 |
| Amazon Polly Neural | $0.016 | $0.18 | ~$11 |
| ElevenLabs (overage) | $0.05–$0.10 | $0.55–$1.10 | ~$33–66, plus a subscription floor |

(Google and Amazon both also give real free tiers — roughly 1M free Neural characters/month
each — that could plausibly cover this project's entire usage on their own.)

This is new spend on top of the existing, unrelated Claude text-generation cost —
`speechSynthesis` is currently $0.

## The decision

**Deferred, not rejected.** For a school project, the cost of the change — a second
vendor account and its own billing, a new server endpoint and secret, a new failure
mode to test and support — outweighs the benefit of fixing a limitation that only
shows up when a phone is locked. Everything else about the app works today, including
in the browser, in the foreground, which covers demoing and normal classroom use.

If this gets picked back up: the sketch above is the plan, the provider comparison
above is the cost basis, and the `tts.js`-internals-only framing is what keeps it from
being a bigger project than it needs to be. Nothing about the current architecture
needs to change in anticipation of this — it was designed so this stays a clean,
addable seam rather than a rewrite, precisely so the decision to defer it wouldn't
foreclose doing it later.
